# Athmetry System Status

A lightweight, static engineering health monitoring website for Athmetry. It
centralizes the development pipeline health of the `athmetry-backend`,
`athmetry-frontend`, and `athmetry-system-status` repositories in one place,
so Athmetry owners can monitor CI/CD health at a glance.

**Live URL (GitHub Pages):**
https://athmetry.github.io/athmetry-system-status/

**Future custom domain:** `status.athmetry.com` (not yet configured)

## Purpose

Give Athmetry owners (2–3 users initially) operational visibility into the
development pipeline health of the backend, frontend, and system status
repositories from a single centralized location. No frameworks, no backend, no
database — just HTML, CSS, vanilla JavaScript, JSON, GitHub Actions, and
GitHub Pages.

## Technology stack

- HTML5
- CSS3
- Vanilla JavaScript (ES modules)
- JSON (`data/status.json`)
- GitHub Actions (status collection, Pages deployment, CI validation, security scanning)
- GitHub Pages (static hosting)

**Explicitly not used:** React/Angular/Vue, Node.js/Express backend, Spring
Boot, databases, paid monitoring services, bundlers, or build steps.

`package.json` exists only for development tooling (`@playwright/test` and the
status JSON validator). The browser application itself has no npm dependencies
and is served directly from the repository root.

## Architecture

1. **Collector workflow** (`.github/workflows/collect-status.yml`)
   - Runs when the Backend reporter updates `data/status-events/backend.json` on `main`, on a 30-minute fallback schedule (`*/30 * * * *`), and on `workflow_dispatch`.
   - Uses a fine-grained GitHub Personal Access Token (`ATHMETRY_GITHUB_TOKEN`)
     stored as a repository Actions secret.
   - Calls the GitHub Actions REST API (`gh api`) to fetch the latest workflow
     runs and job details for `athmetry-backend`, `athmetry-frontend`, and
     `athmetry-system-status` on the `main` branch.
   - Normalizes the data and writes `data/status.json`.
   - Commits and pushes `data/status.json` **only when the data has changed**.
   - **Self-monitoring**: The collector's own workflow (`collect-status.yml`)
     is included for the `athmetry-system-status` repository. Because a run
     always observes itself as `in_progress`, the most recent **completed** run
     is reported instead, so failed collector runs stay visible without pinning
     the dashboard to "Running".
2. **Website** (`index.html` + `css/` + `js/`)
   - Reads `data/status.json` and renders backend, frontend, and system status
     health, commit info, job status, execution history, and links to GitHub
     Actions runs.
   - Auto-refreshes every 60 seconds without reloading the page.
   - Shows a warning if the JSON cannot be retrieved or is stale.
   - Dashboard layout: Backend (left column), System Status (top-right),
     Frontend (bottom-right). All three cards use the monitor/computer icon.
     Pipeline counts and branch names are dynamic. Product tags:
     `ATHMETRY-WEB` (Backend/Frontend) and `ATHMETRY-SYSTEM-STATUS` (System
     Status).
3. **Deployment workflow** (`.github/workflows/deploy-pages.yml`)
   - Triggers on `workflow_run` completion of `Security Scan` or
     `Collect System Status` on `main` (there is no `push` trigger: commits
     made with the built-in `GITHUB_TOKEN` do not trigger `push` workflows).
   - **Quality gate**: deploys only when the triggering run succeeded on `main`
     and the current `main` head is the latest Security-Scan-validated revision,
     or differs from it only by `data/status.json`. Pull requests,
     failed/cancelled runs, stale revisions, diverged history and duplicate
     deploys are blocked.
   - Checks out the exact validated SHA, verifies `git rev-parse HEAD`, then
     deploys with `actions/upload-pages-artifact` and `actions/deploy-pages`.
4. **Security Scan workflow** (`.github/workflows/security-scan.yml`)
   - Runs on pull requests, pushes to `main`, a weekly schedule, and manual
     dispatch.
   - Runs Gitleaks against tracked files and zizmor against the workflow
     definitions. Findings fail the workflow; secret values are redacted.
   - References are governed by `.github/zizmor.yml` (SHA pinning for
     third-party actions and `actions/checkout`; the two official Pages actions
     retain their existing major-version tags).

The System Status repository's own `collect-status.yml`, `deploy-pages.yml`,
and `security-scan.yml` are all discoverable by the collector and appear on its
dashboard card.

## Supported statuses

Success, Failure, In Progress, Queued, Cancelled, Skipped, Unknown / No
workflow found. An assumed successful status is **never** shown when data is
missing.

## GitHub authentication setup

### Required repository secret

In the `athmetry-system-status` repository, go to **Settings → Secrets and
variables → Actions → New repository secret** and add:

| Secret name | Value |
|-------------|-------|
| `ATHMETRY_GITHUB_TOKEN` | A fine-grained GitHub Personal Access Token |

### Token permissions

The fine-grained PAT must have:

- **Repository permissions** (read-only) on `athmetry/athmetry-backend`,
  `athmetry/athmetry-frontend`, and `athmetry/athmetry-system-status`:
  - Actions: read
  - Contents: read
- **Repository permissions** on `athmetry/athmetry-system-status`:
  - Contents: read and write (to commit `data/status.json`)

Never hardcode or commit the token. It is never exposed in JavaScript, HTML,
CSS, JSON, the README, or any generated file.

### Required permissions on the status repository

The `collect-status.yml` workflow uses `permissions: contents: write` so it can
commit updated status data. The `deploy-pages.yml` workflow uses
`permissions: pages: write` and `id-token: write`.

The monitored repositories (`athmetry-backend`, `athmetry-frontend`,
`athmetry-system-status`) already run their CI with
`permissions: contents: read` — no changes are needed there, and this project
does not modify them.

## GitHub Pages configuration

1. In the `athmetry-system-status` repository, go to **Settings → Pages**.
2. Under **Build and deployment**, set **Source** to **GitHub Actions**.
3. The `deploy-pages.yml` workflow will handle builds and deployments on pushes
   to `main`.
4. The site will be published at:
   https://athmetry.github.io/athmetry-system-status/

### Future custom domain (`status.athmetry.com`)

The `CNAME` file is reserved for the future custom domain. Do **not** add
`status.athmetry.com` to `CNAME` or configure DNS until you own the domain and
are ready to configure it, as doing so prematurely would break the default
GitHub Pages URL.

## Collector triggers

- Event-driven: a Backend reporter push to
  `data/status-events/backend.json` on `main` starts collection promptly.
- Scheduled fallback: every 30 minutes (`*/30 * * * *` cron).
- Manual: via the **Actions → Collect System Status → Run workflow** button in
  the GitHub UI (`workflow_dispatch`).

The collector commits only `data/status.json`, so its own output does not match
the event push path and cannot trigger another collector run.

The collector runs independently of GitHub Pages refresh frequency.

**Self-monitoring**: The collector's own workflow (`collect-status.yml`) is
included for the `athmetry-system-status` repository. Its most recent
**completed** run is reported so the card shows real health instead of the
collector's own in-progress execution. Other repositories' workflows are
included unchanged.

## Release version

The footer release label is **not hardcoded**. `fetchReleaseVersion()` in
`js/app.js` fetches `package.json` and renders `Release v<major>.<minor>` (for
example `1.0.0` → `Release v1.0`). If `package.json` cannot be fetched or has no
`version`, the placeholder `Release v—` remains.

To release a new version, update `version` in `package.json` only. Do not add a
hardcoded version anywhere in `index.html` or JavaScript.

## Visitor IP lookup

The footer optionally shows the visitor IP and approximate location using
`https://ipwho.is/` (5-second timeout, non-blocking). The lookup sends the
visitor IP to that third-party service. If the request fails, is blocked, or
returns an unusable payload, the footer shows `Visitor IP: Unavailable` and
`Approx. Location: Unavailable`; the dashboard is never blocked.

## How to test manually

1. Clone this repository locally.
2. Serve the static files (e.g. `python3 -m http.server 8000` from the repo
   root) and open `http://localhost:8000/index.html`.
3. The dashboard renders the last committed `data/status.json`. Statuses are
   shown as collected; missing data is shown as "Unknown", never assumed
   successful.
4. To test the collector locally, ensure `gh` and `jq` are installed, set
   `ATHMETRY_GITHUB_TOKEN`, and run:
   ```bash
   ./.github/scripts/collect-status.sh
   ```
   The script overwrites `data/status.json` in the working tree but does not
   commit or push. Back up the file first if you need to preserve the current
   data.
5. Validate the JSON and its data contract:
   ```bash
   jq . data/status.json > /dev/null && echo "valid JSON"
   node scripts/validate-status-json.js
   ```
6. Optional browser regression testing uses the installed Playwright package:
   ```bash
   npx playwright --version
   ```
   Committed Playwright tests cover Manual Refresh success, failure, timeout,
   cache busting, and retention of valid dashboard data. See
   `docs/development/TESTING_GUIDE.md` for the full checklist.

## How to add additional repositories and branches

The collector is configured through variables rather than code changes:

1. Edit `.github/scripts/collect-status.sh` and add entries to the
   `MONITORED_REPOS` array in the format:
   `"repo_name owner repo"`.
2. To monitor a different branch, change the `BRANCH` variable (or make it
   per-repo in a future iteration).
3. Ensure the `ATHMETRY_GITHUB_TOKEN` has read access to the new repository
   (Actions: Read, Contents: Read).
4. Commit and push. The collector will pick up the new repositories on its next
   run.

**Self-monitoring**: The collector reports the most recent **completed** run of
its own `collect-status.yml` so the card reflects real health rather than the
collector's in-progress execution.

## Troubleshooting

| Issue | Likely cause / fix |
|-------|-------------------|
| Dashboard shows "Unable to load status data" | `data/status.json` missing or not yet committed. Run the collector workflow once. |
| Status is "Unknown" for a repo | No workflow runs found on the monitored branch, or the token lacks read access to that repo. |
| Collector fails to commit | `ATHMETRY_GITHUB_TOKEN` lacks `contents: write` on this repo. |
| Pages site not updating | Ensure Pages source is set to "GitHub Actions" in repo settings. |
| Stale data warning | The collector has not published data recently. Backend events normally trigger prompt collection; the 30-minute schedule is the fallback. Check the Actions tab for failures. |
| System Status repo shows no pipelines | The `athmetry-system-status` repository may not have any workflows on `main`, or the collector hasn't run since adding it. |
| Footer shows `Release v—` | `package.json` could not be fetched. Check that the file is deployed and served with the site. |
| Visitor IP shows "Unavailable" | `ipwho.is` is blocked, rate-limited, or unreachable. This is non-blocking and expected in some networks. |

## Development notes

- Do not modify `athmetry-backend` or `athmetry-frontend`.
- Do not commit or expose `ATHMETRY_GITHUB_TOKEN`.
- Do not fabricate pipeline results; missing data is shown as "Unknown".
- Future phases (API health, Vercel, mobile, infrastructure) are deliberately
  not implemented. The data structure is designed to extend without rebuilding.
