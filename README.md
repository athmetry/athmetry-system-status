# Athmetry System Status

A lightweight, static engineering health monitoring website for Athmetry. It
centralizes the development pipeline health of the `athmetry-backend` and
`athmetry-frontend` repositories in one place, so Athmetry owners can monitor
CI/CD health at a glance.

**Live URL (GitHub Pages):**
https://athmetry.github.io/athmetry-system-status/

**Future custom domain:** `status.athmetry.com` (not yet configured)

## Purpose

Give Athmetry owners (2–3 users initially) operational visibility into the
development pipeline health of the backend and frontend repositories from a
single centralized location. No frameworks, no backend, no database — just
HTML, CSS, vanilla JavaScript, JSON, GitHub Actions, and GitHub Pages.

## Technology stack

- HTML5
- CSS3
- Vanilla JavaScript (ES modules)
- JSON (`data/status.json`)
- GitHub Actions (status collection + Pages deployment)
- GitHub Pages (static hosting)

**Explicitly not used:** React/Angular/Vue, Node.js/Express backend, Spring
Boot, databases, paid monitoring services, or unnecessary dependencies.

## Architecture

1. **Collector workflow** (`.github/workflows/collect-status.yml`)
   - Runs on a schedule (`*/5 * * * *`, every 5 minutes) and on `workflow_dispatch`.
   - Uses a fine-grained GitHub Personal Access Token (`ATHMETRY_GITHUB_TOKEN`)
     stored as a repository Actions secret.
   - Calls the GitHub Actions REST API (`gh api`) to fetch the latest workflow
     runs and job details for `athmetry-backend` and `athmetry-frontend` on the
     `main` branch.
   - Normalizes the data and writes `data/status.json`.
   - Commits and pushes `data/status.json` **only when the data has changed**.
2. **Website** (`index.html` + `css/` + `js/`)
   - Reads `data/status.json` and renders backend/frontend health, commit info,
     job status, execution history, and links to GitHub Actions runs.
   - Auto-refreshes every 60 seconds without reloading the page.
   - Shows a warning if the JSON cannot be retrieved or is stale.
3. **Deployment workflow** (`.github/workflows/deploy-pages.yml`)
   - Deploys the static site to GitHub Pages using `actions/upload-pages-artifact`
     and `actions/deploy-pages`.

## Supported statuses

Success, Failure, In Progress, Queued, Cancelled, Skipped, Unknown / No
workflow found. An assumed successful status is **never** shown when data is
missing.

## GitHub authentication setup

### Required repository secret

In the `athmetry-system-status` repository, go to **Settings → Secrets and
variables → Actions → New repository secret** and add:

| Secret name | Value |
|-------------|-------|
| `ATHMETRY_GITHUB_TOKEN` | A fine-grained GitHub Personal Access Token |

### Token permissions

The fine-grained PAT must have:

- **Repository permissions** (read-only) on `athmetry/athmetry-backend` and
  `athmetry/athmetry-frontend`:
  - Actions: read
  - Contents: read
- **Repository permissions** on `athmetry/athmetry-system-status`:
  - Contents: read and write (to commit `data/status.json`)

Never hardcode or commit the token. It is never exposed in JavaScript, HTML,
CSS, JSON, the README, or any generated file.

### Required permissions on the status repository

The `collect-status.yml` workflow uses `permissions: contents: write` so it can
commit updated status data. The `deploy-pages.yml` workflow uses
`permissions: pages: write` and `id-token: write`.

The monitored repositories (`athmetry-backend`, `athmetry-frontend`) already
run their CI with `permissions: contents: read` — no changes are needed there,
and this project does not modify them.

## GitHub Pages configuration

1. In the `athmetry-system-status` repository, go to **Settings → Pages**.
2. Under **Build and deployment**, set **Source** to **GitHub Actions**.
3. The `deploy-pages.yml` workflow will handle builds and deployments on pushes
   to `main`.
4. The site will be published at:
   https://athmetry.github.io/athmetry-system-status/

### Future custom domain (`status.athmetry.com`)

The `CNAME` file is reserved for the future custom domain. Do **not** add
`status.athmetry.com` to `CNAME` or configure DNS until you own the domain and
are ready to configure it, as doing so prematurely would break the default
GitHub Pages URL.

## Collector schedule

- Automatic: every 5 minutes (`*/5 * * * *` cron).
- Manual: via the **Actions → Collect System Status → Run workflow** button in
  the GitHub UI (`workflow_dispatch`).

The collector runs independently of GitHub Pages refresh frequency.

## Data format (`data/status.json`)

The collector generates this structure (schema version 1):

```json
{
  "schemaVersion": 1,
  "collectedAt": "2026-11-11T21:00:00Z",
  "monitoredBranch": "main",
  "repositories": [
    {
      "name": "athmetry-backend",
      "owner": "athmetry",
      "repo": "athmetry-backend",
      "error": null,
      "latestRun": {
        "status": "success",
        "conclusion": "success",
        "runNumber": 42,
        "runUrl": "https://github.com/athmetry/athmetry-backend/actions/runs/12345",
        "commitSha": "abc1234",
        "commitMessage": "Fix bug",
        "commitAuthor": "Name",
        "startedAt": "2026-11-11T20:55:00Z",
        "completedAt": "2026-11-11T20:58:00Z",
        "jobs": [
          { "name": "verify", "status": "success", "conclusion": "success" }
        ]
      },
      "history": [ ... ]
    }
  ]
}
```

The website reads this file directly.

## How to test manually

1. Clone this repository locally.
2. Serve the static files (e.g. `python3 -m http.server 8000` from the repo
   root) and open `http://localhost:8000/index.html`.
3. Since `data/status.json` initially contains no run data, the dashboard will
   show "Unknown" statuses — this is expected until the collector runs.
4. To test the collector locally, ensure `gh` and `jq` are installed, set
   `ATHMETRY_GITHUB_TOKEN`, and run:
   ```bash
   ./.github/scripts/collect-status.sh
   ```
   Then inspect `data/status.json`.
5. Validate the JSON:
   ```bash
   jq . data/status.json > /dev/null && echo "valid JSON"
   ```

## How to add additional repositories and branches

The collector is configured through variables rather than code changes:

1. Edit `.github/scripts/collect-status.sh` and add entries to the
   `MONITORED_REPOS` array in the format:
   `"repo_name owner repo"`.
2. To monitor a different branch, change the `BRANCH` variable (or make it
   per-repo in a future iteration).
3. Commit and push. The collector will pick up the new repositories on its next
   run.

## Troubleshooting

| Issue | Likely cause / fix |
|-------|-------------------|
| Dashboard shows "Unable to load status data" | `data/status.json` missing or not yet committed. Run the collector workflow once. |
| Status is "Unknown" for a repo | No workflow runs found on the monitored branch, or the token lacks read access to that repo. |
| Collector fails to commit | `ATHMETRY_GITHUB_TOKEN` lacks `contents: write` on this repo. |
| Pages site not updating | Ensure Pages source is set to "GitHub Actions" in repo settings. |
| Stale data warning | Collector hasn't run recently (every 5 min). Check the Actions tab for failures. |

## Development notes

- Do not modify `athmetry-backend` or `athmetry-frontend`.
- Do not commit or expose `ATHMETRY_GITHUB_TOKEN`.
- Do not fabricate pipeline results; missing data is shown as "Unknown".
- Future phases (API health, Vercel, mobile, infrastructure) are deliberately
  not implemented. The data structure is designed to extend without rebuilding.
